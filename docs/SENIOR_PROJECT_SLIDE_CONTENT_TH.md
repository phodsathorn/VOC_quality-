## สไลด์ 2: Why — ทำไมเรื่องนี้จึงสำคัญ?

### ข้อความบนสไลด์

- โครงงานมุ่งติดตามคุณภาพอากาศในพื้นที่พ่นสีฝุ่น ซึ่งต้องพิจารณาฝุ่นละอองร่วมกับสัญญาณจากก๊าซและสารระเหย
- การวัดเพียงตัวแปรเดียวให้ข้อมูลไม่ครบสำหรับการแยกสภาพอากาศแต่ละประเภท
- ข้อมูลที่บันทึกต่อเนื่องช่วยให้ผู้ดูแลเห็นช่วงเวลาที่ค่าผิดปกติและตรวจสอบย้อนหลังได้
- จึงเสนอระบบที่รวมเซ็นเซอร์หลายชนิดกับการวิเคราะห์ข้อมูลและการแสดงผลผ่านเว็บไซต์

หมายเหตุผู้บรรยาย: อธิบายว่าเป็นที่มาของโจทย์โครงงาน ยังไม่ได้สรุปว่าพื้นที่ใดมีสารชนิดใดหรือเกินเกณฑ์โดยไม่มีข้อมูลวัดจริง

แหล่งข้อมูล: README.md, PROJECT_INFO.md

## สไลด์ 3: Who — ใครคือผู้ใช้งานเป้าหมาย?

### ข้อความบนสไลด์

- **ผู้ปฏิบัติงานในพื้นที่พ่นสี:** ต้องการทราบสถานะอากาศระหว่างการทำงาน
- **ผู้ดูแลพื้นที่และเจ้าหน้าที่ความปลอดภัย:** ต้องการติดตามค่าที่เปลี่ยนแปลงและตรวจสอบเหตุการณ์ย้อนหลัง
- **ฝ่ายซ่อมบำรุง:** ต้องการใช้แนวโน้มข้อมูลประกอบการตรวจระบบระบายอากาศ
- **ผู้พัฒนาระบบ:** ต้องการข้อมูลพร้อมป้ายกำกับสำหรับฝึกและประเมินโมเดล

หมายเหตุผู้บรรยาย: เป็นกลุ่มผู้ใช้ที่เสนอสำหรับโครงงาน ต้องยืนยันความต้องการผ่านการพูดคุยหรือทดลองใช้งานจริง

แหล่งข้อมูล: PROJECT_INFO.md, docs/web_platform_spec.md

## สไลด์ 4: How — ช่องว่างของการติดตามคุณภาพอากาศ

### ข้อความบนสไลด์

- การตรวจเป็นครั้งคราวอาจไม่มีข้อมูลในช่วงที่ค่าเปลี่ยนแปลง
- ข้อมูลจากอุปกรณ์หลายตัวอาจอยู่คนละจุด ทำให้เปรียบเทียบตามเวลาได้ยาก
- การใช้เกณฑ์กับค่าจากเซ็นเซอร์เพียงช่องเดียวอาจแยกสภาพอากาศได้จำกัด
- ข้อมูลที่ไม่มีเวลาและป้ายกำกับชัดเจนทำให้นำกลับไปฝึกโมเดลได้ยาก

หมายเหตุผู้บรรยาย: ใช้คำว่า “ช่องว่างที่โครงงานต้องการแก้” แทนการกล่าวโทษพฤติกรรมของคนทำงาน ประเด็นเหล่านี้เป็นสมมติฐานความต้องการที่ต้องตรวจสอบกับพื้นที่เป้าหมาย

แหล่งข้อมูล: สังเคราะห์จากเป้าหมายใน PROJECT_INFO.md และ docs/ml_model_analysis.md

## สไลด์ 5: What — ปัญหาที่โครงงานต้องการแก้

### ข้อความบนสไลด์

**การขาดข้อมูลที่เชื่อมโยงการวัดอากาศ การจำแนกสภาพอากาศ และการติดตามย้อนหลังไว้ในระบบเดียว**

- ผู้ใช้ต้องการเห็นค่าจากหลายเซ็นเซอร์ในช่วงเวลาเดียวกัน
- ผู้ใช้ต้องการข้อมูลประกอบการแยกสภาพปกติออกจากเหตุการณ์ผิดปกติ
- ผู้พัฒนาต้องการชุดข้อมูลที่ตรวจสอบแหล่งที่มาและนำไปประเมินโมเดลได้

ภาพแนะนำ: ตัวอย่างเส้นเวลาเหตุการณ์หนึ่งช่วง พร้อมตำแหน่งที่ต้องบันทึกค่าและป้ายกำกับ โดยระบุว่าเป็นภาพอธิบาย

แหล่งข้อมูล: PROJECT_INFO.md, vocs-website/README.md

## สไลด์ 6: วัตถุประสงค์

### ข้อความบนสไลด์

1. พัฒนาต้นแบบกล่องตรวจวัดที่รวมเซ็นเซอร์ฝุ่น ก๊าซ และสภาพแวดล้อมด้วย ESP32
2. พัฒนาเว็บไซต์สำหรับแสดงค่า บันทึกข้อมูลย้อนหลัง และจัดการข้อมูลการทดลอง
3. พัฒนาและประเมินโมเดลจำแนกสภาพอากาศจากข้อมูลเซ็นเซอร์หลายช่อง
4. เปรียบเทียบวิธีใช้เซ็นเซอร์อาร์เรย์กับวิธีใช้เกณฑ์พื้นฐานบนข้อมูลทดสอบชุดเดียวกัน

หมายเหตุผู้บรรยาย: การนำโมเดลไปรันบน ESP32 เป็นเป้าหมายระยะต่อยอด หลังจากยืนยันผลบนเซิร์ฟเวอร์และตรวจข้อจำกัดของอุปกรณ์

แหล่งข้อมูล: PROJECT_INFO.md, docs/ml_model_analysis.md

## สไลด์ 7: Solution — แนวทางที่เสนอ

### ข้อความบนสไลด์

- **ตรวจวัดหลายมิติ:** รวมข้อมูลฝุ่น สัญญาณก๊าซ อุณหภูมิ และความชื้น
- **วิเคราะห์รูปแบบข้อมูล:** ใช้ Machine Learning จำแนกสภาพอากาศตามกลุ่มที่มีข้อมูลทดลองรองรับ
- **ติดตามผ่านเว็บไซต์:** แสดงค่าล่าสุด กราฟย้อนหลัง และสถานะการแจ้งเตือน
- **ปรับปรุงด้วยข้อมูลรอบใหม่:** เก็บข้อมูลพร้อมป้ายกำกับ แล้วฝึกและตรวจสอบโมเดลใหม่ก่อนนำมาใช้งาน

หมายเหตุผู้บรรยาย: “Adaptive” ในแนวทางนี้หมายถึงการปรับโมเดลผ่านรอบเก็บข้อมูลและฝึกใหม่ ไม่ใช่การเรียนรู้อัตโนมัติตลอดเวลาที่ทำสำเร็จแล้ว

แหล่งข้อมูล: PROJECT_INFO.md, vocs-website/README.md

## สไลด์ 8: System Architecture — สถาปัตยกรรมระบบ

### ข้อความบนสไลด์

1. **Sensor Array:** ตรวจวัดและส่งข้อมูลเข้า ESP32
2. **ESP32:** อ่านค่า ตรวจสถานะ และส่งข้อมูลผ่าน Wi-Fi ด้วย HTTP API
3. **FastAPI และ PostgreSQL:** รับข้อมูล จัดเก็บ และเรียกใช้โมเดลบนเซิร์ฟเวอร์
4. **Web Dashboard:** แสดงค่าล่าสุด ประวัติข้อมูล และผลการจำแนก
5. **Data Collection และ Model Training:** จัดป้ายกำกับ ส่งออกข้อมูล และฝึกโมเดลรุ่นถัดไป

ภาพแนะนำ: แผนภาพลำดับ Sensor Array / ESP32 / API / Database / Dashboard และเส้นทางข้อมูลจาก Database ไป Model Training

หมายเหตุผู้บรรยาย: โค้ดมีทั้งการส่ง HTTP จาก ESP32 และสคริปต์สะพาน Serial ไป HTTP ส่วนชุดเซ็นเซอร์ Rev A ต้องเพิ่มไดรเวอร์และปรับโครงสร้างข้อมูลก่อนเชื่อมครบ การส่งโมเดลกลับไปรันบนบอร์ดยังเป็นแผนต่อยอด

แหล่งข้อมูล: src/air_quality_monitor/air_quality_monitor.ino, esp32_to_web.py, vocs-website/backend/model_loader.py

## สไลด์ 12: Model Scope — ขอบเขตแบบจำลอง

### ข้อความบนสไลด์

- **ข้อมูลนำเข้า:** ค่าฝุ่น สัญญาณตอบสนองของก๊าซ อุณหภูมิ และความชื้น
- **แนวทางเริ่มต้น:** ใช้ Random Forest บนเซิร์ฟเวอร์เป็นโมเดลพื้นฐาน
- **กลุ่มเป้าหมายที่เสนอ:** สภาพปกติ ฝุ่นสี ไอระเหยสารทำละลาย และควัน ตามข้อมูลทดลองที่จัดเก็บได้
- **ผลลัพธ์:** กลุ่มที่โมเดลทำนายและคะแนนความเชื่อมั่น
- **แนวทางต่อยอด:** เปรียบเทียบ MLP และพิจารณานำโมเดลที่เหมาะสมลง ESP32

หมายเหตุผู้บรรยาย: สคริปต์ปัจจุบันเรียนรู้คลาสจาก label ในไฟล์ข้อมูล ยังไม่ได้ยืนยันว่ามีข้อมูลครบสี่กลุ่ม ต้องปรับ feature และฝึกใหม่เมื่อเปลี่ยนเป็นชุด Rev A คะแนนความเชื่อมั่นต้องประเมินก่อนใช้เป็นเกณฑ์ตัดสินใจ

แหล่งข้อมูล: vocs-website/ml/train_model.py, vocs-website/backend/model_loader.py, docs/ml_model_analysis.md

- บันทึกเวลา รหัสอุปกรณ์ รหัสรอบทดลอง และป้ายกำกับสภาพอากาศ
- เก็บข้อมูลช่วงพื้นฐาน ช่วงเหตุการณ์ และช่วงฟื้นตัวของเซ็นเซอร์
- แยกชุดฝึกและชุดทดสอบตามรอบทดลองหรือวัน เพื่อประเมินกับรอบที่โมเดลไม่เคยเห็น
- กำหนดจำนวนรอบและระยะเวลาเก็บข้อมูลหลังทดลองนำร่อง

หมายเหตุผู้บรรยาย: ไม่ใส่จำนวนข้อมูลที่ยังไม่ได้เก็บจริง หากทำการทดลองกับสารหรือควัน ต้องใช้แผนทดลองและสถานที่ที่ผู้ดูแลอนุญาต ไม่สร้างการสัมผัสเพื่อการสาธิตโดยไม่มีการควบคุม

แหล่งข้อมูล: PROJECT_INFO.md, docs/ml_model_analysis.md, vocs-website/README.md

## สไลด์ 14: Data Features — คุณลักษณะที่ใช้วิเคราะห์

### ข้อความบนสไลด์

| กลุ่มข้อมูล | ตัวอย่างคุณลักษณะ | จุดประสงค์ |
|---|---|---|
| ฝุ่นละออง | PM2.5, PM10 | ประกอบการแยกเหตุการณ์ที่มีฝุ่น |
| ก๊าซและสารระเหย | ค่าตอบสนอง SGP41, BME680 และ MiCS-6814 | สร้างรูปแบบการตอบสนองหลายช่อง |
| สภาพแวดล้อม | อุณหภูมิและความชื้น | ประกอบการวิเคราะห์การเปลี่ยนแปลงของสัญญาณ |
| การเปลี่ยนแปลงตามเวลา | ค่าเฉลี่ย การเปลี่ยนจากพื้นฐาน และความชัน | อธิบายลักษณะก่อนและระหว่างเหตุการณ์ |

ช่อง ZE03-O3 และ ZE03-CO ใช้ติดตามค่าก๊าซเฉพาะตามการตั้งค่าและการตรวจสอบของโมดูล

หมายเหตุผู้บรรยาย: ตารางเป็นแนวทาง feature ของ Rev A ต้องยืนยันชนิดข้อมูล หน่วย และความพร้อมของไดรเวอร์ก่อนฝึกโมเดล ค่า gas resistance หรือสัญญาณดิบไม่ใช่ความเข้มข้น VOC แบบ ppm โดยตรง

แหล่งข้อมูล: hardware/production_modules/README.md, docs/ml_model_analysis.md

## สไลด์ 15: Key Metrics — ตัวชี้วัดประสิทธิภาพ

### ข้อความบนสไลด์

- **Macro F1-score:** สรุปคุณภาพการจำแนกโดยให้ความสำคัญแต่ละกลุ่มเท่ากัน
- **Recall รายกลุ่ม:** ตรวจว่าระบบพลาดเหตุการณ์แต่ละประเภทมากน้อยเพียงใด
- **อัตราแจ้งเตือนผิด:** จำนวนการแจ้งเตือนในช่วงปกติต่อชั่วโมงทดสอบ
- **ระยะเวลาหน่วง:** เวลาจากเหตุการณ์ตามนิยามการทดลองจนระบบแสดงผล
- **ความครบถ้วนของข้อมูล:** สัดส่วนข้อมูลที่ได้รับเทียบกับจำนวนที่ควรได้รับ

หมายเหตุผู้บรรยาย: นำเสนอ Accuracy และ Confusion Matrix ประกอบในรายงานผล ไม่ใส่ค่าความแม่นยำหรือเป้าหมายผ่านเกณฑ์เป็นผลสำเร็จก่อนทดสอบ

แหล่งข้อมูล: vocs-website/ml/train_model.py และแผนการประเมินที่เสนอสำหรับโครงงาน

## สไลด์ 16: Benchmarking — เกณฑ์เปรียบเทียบ

### ข้อความบนสไลด์

| วิธีเปรียบเทียบ | คำถามที่ต้องการตอบ |
|---|---|
| เกณฑ์จากเซ็นเซอร์เดี่ยว | การอ่านค่าเพียงช่องเดียวแยกเหตุการณ์ได้เพียงใด |
| เกณฑ์จากหลายเซ็นเซอร์ | การรวมข้อมูลด้วยกฎพื้นฐานช่วยได้เพียงใด |
| Random Forest จากอาร์เรย์ | การเรียนรู้รูปแบบช่วยเพิ่มคุณภาพการจำแนกหรือไม่ |
| MLP หากพัฒนาได้ในเวลาโครงงาน | ให้ผลและใช้ทรัพยากรเหมาะกับ ESP32 หรือไม่ |

ทุกวิธีใช้ชุดทดสอบและนิยามเหตุการณ์เดียวกัน โดยกำหนดเกณฑ์จากชุดฝึกหรือชุดตรวจสอบก่อนเปิดชุดทดสอบ

หมายเหตุผู้บรรยาย: เป็นแผนเปรียบเทียบ ไม่ใช่ข้อสรุปว่า ML ดีกว่ากฎพื้นฐานแล้ว การเปรียบเทียบค่าความเข้มข้นต้องใช้เครื่องอ้างอิงที่เหมาะสมเพิ่มเติม

แหล่งข้อมูล: docs/ml_model_analysis.md, vocs-website/ml/train_model.py

## สไลด์ 17: Evaluation Methodology — วิธีการวัดผล

### ข้อความบนสไลด์

1. ตรวจสถานะเซ็นเซอร์ อุ่นเครื่อง และบันทึกค่าพื้นฐานก่อนแต่ละรอบ
2. เก็บข้อมูลแต่ละเงื่อนไขพร้อมป้ายกำกับและทำซ้ำหลายรอบ
3. แยกชุดข้อมูลตามรอบทดลอง แล้วฝึกและปรับโมเดลด้วยชุดฝึกและชุดตรวจสอบ
4. ประเมินครั้งสุดท้ายกับชุดทดสอบที่กันไว้ และเปรียบเทียบกับวิธีพื้นฐาน
5. สรุปผลการจำแนก การแจ้งเตือน ระยะเวลาหน่วง และการส่งข้อมูลทั้งระบบ

หมายเหตุผู้บรรยาย: สคริปต์ train_model.py ปัจจุบันสุ่มแบ่งข้อมูลเป็นรายแถว แผนโครงงานเสนอให้เปลี่ยนเป็นการแบ่งตาม session หรือวันก่อนรายงานผลจริง เพื่อลดการปะปนของข้อมูลที่อยู่ใกล้กัน

แหล่งข้อมูล: vocs-website/ml/train_model.py, PROJECT_INFO.md, docs/ml_model_analysis.md

## สไลด์ 20: Q&A

### ข้อความบนสไลด์

**Q&A**

คำถามและข้อเสนอแนะ

### แนวตอบสำหรับผู้บรรยาย ไม่ต้องใส่บนสไลด์

- **ทำไมต้องใช้หลายเซ็นเซอร์?** เพื่อทดสอบว่ารูปแบบตอบสนองร่วมกันให้ข้อมูลสำหรับจำแนกมากกว่าการอ่านค่าเพียงช่องเดียวหรือไม่
- **วัด VOC เป็น ppm ได้หรือไม่?** ขอบเขตหลักคือการจำแนกสภาพอากาศ ส่วนการวัดความเข้มข้นต้องมีการสอบเทียบและเครื่องอ้างอิงที่เหมาะสม
- **โมเดลใช้อะไร?** โค้ดปัจจุบันมี Random Forest บนเซิร์ฟเวอร์ ส่วน MLP และ TinyML เป็นแนวทางต่อยอด
- **ความแม่นยำเท่าไร?** ยังไม่มีผลทดสอบที่ยืนยันในเอกสารที่ตรวจ ต้องรายงานจากชุดทดสอบที่กันไว้หลังเก็บข้อมูล
- **ใช้งานโรงงานได้ทันทีหรือไม่?** เป็นต้นแบบที่ต้องเชื่อมระบบและประเมินภาคสนาม ยังไม่มีการรับรองเป็นระบบเตือนภัยอุตสาหกรรม
