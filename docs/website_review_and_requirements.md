# รีวิวเว็บและข้อกำหนดการพัฒนาต่อ

อัปเดต: 18 ตุลาคม 2569

## เป้าหมาย

เว็บ VOC / E-Nose ต้องช่วยผู้ปฏิบัติงานตอบคำถามได้เร็วว่า **อากาศตอนนี้เป็นอย่างไร, อุปกรณ์ตัวไหนเริ่มเสื่อม, ควรเปลี่ยนเมื่อใด, เหลือเวลาใช้งานประมาณกี่วัน และต้องเตรียมอะไหล่อะไร** พร้อมเปิดดูบันทึกคุณภาพอากาศย้อนหลังรายวันได้

## สิ่งที่ตรวจพบในเว็บปัจจุบัน

- Dashboard แสดงค่าล่าสุด, สถานะกล่อง, AI, alerts และกราฟ TVOC/PM2.5 ย้อนหลังเพียง 15 นาที / 1 ชั่วโมง / 24 ชั่วโมง
- มีหน้า Maintenance ที่แสดง Health Index (HI), Remaining Useful Life (RUL), กำหนดสอบเทียบ และไส้กรอง พร้อมรายการงานที่ใกล้ถึงกำหนด
- ข้อมูล Maintenance ยังมี fallback เป็นข้อมูลจำลอง และข้อมูลจำลองถูกคำนวณจากอายุ/Drift/Noise ที่ตั้งไว้ ไม่ใช่แนวโน้มการเสื่อมที่เรียนจากข้อมูลจริง จึงห้ามสื่อว่าเป็นวันเปลี่ยนจริงโดยไม่แสดงแหล่งข้อมูลและความเชื่อมั่น
- หน้า Dashboard ยังไม่มีตัวเลือกวัน/ช่วงวันที่และสรุปรายวันสำหรับค้นย้อนหลัง
- ฐานข้อมูลเก็บ sensor readings แบบ time-series พร้อมเวลาและ box_id แต่ยังไม่มีตารางบันทึกเหตุการณ์ซ่อม/เปลี่ยนชิ้นส่วนหรืออะไหล่คงเหลือ
- Backend ปัจจุบันลบ readings เก่ากว่า 30 วันโดยอัตโนมัติ จึงไม่สอดคล้องกับการเปิดย้อนหลังระยะยาว
- หน้าปัจจุบันมีข้อความอธิบายและชื่อหัวข้อภาษาอังกฤษจำนวนมากเมื่อเทียบกับงานหลักที่ผู้ใช้ต้องทำ

## รูปแบบที่ได้จากการทบทวนระบบอ้างอิง

- **Air4Thai / กรมควบคุมมลพิษ:** แสดงระดับสีและค่าปัจจุบันแยกตามพื้นที่/สถานี; มีข้อมูลรายชั่วโมงและข้อมูลย้อนหลังในแอป/หน้าเว็บ รายงานช่วงย้อนหลังและพยากรณ์ช่วยวางแผนได้
- **ระบบข้อมูล PCD (AQM Thai):** ให้เลือกสถานี/พารามิเตอร์/ช่วงเริ่มต้น–สิ้นสุด และระดับรายชั่วโมง รายวัน รายเดือน รายปี เหมาะกับการค้นข้อมูลย้อนหลัง
- **US EPA AirData:** แยกข้อมูล Real-time, Hourly, Daily และ Annual; ให้เลือกมลพิษ/ปี/พื้นที่/สถานี และมีกราฟ/รายงาน/ดาวน์โหลด
- **European Environment Agency (EEA):** แสดงทั้งรายชั่วโมงและรายวันระดับสถานี ระบุความครอบคลุมข้อมูลของค่าเฉลี่ยรายวัน และเตือนว่าข้อมูลอาจยังไม่ผ่านการตรวจสอบ

### หลักการที่นำมาใช้กับโปรเจกต์

นำรูปแบบเลือกสถานี/อุปกรณ์ + มลพิษ + วัน/ช่วงวัน + ความละเอียดเวลา, กราฟแนวโน้ม, สีระดับความเสี่ยง, สรุปตัวเลขสำคัญ และสถานะความครบถ้วนของข้อมูลมาใช้ โดยแยก **ค่าที่เซนเซอร์วัดได้** ออกจาก **ดัชนี/ระดับสี** และแสดงเวลาที่วัด/อัปเดต หน่วย และสถานะข้อมูลชัดเจน ไม่ตีความข้อมูลเซนเซอร์ต้นทุนต่ำเป็นค่ามาตรฐานรับรองโดยอัตโนมัติ

## ข้อเสนอ UI: เรียบง่ายและเห็นงานสำคัญก่อน

### 1. Dashboard

ลำดับที่แนะนำ:

1. แถบหัวหน้า: ชื่อกล่อง/พื้นที่, Online/Offline, เวลาอัปเดต
2. การ์ดสถานะใหญ่: คุณภาพอากาศโดยรวม (ข้อความ + สี + ค่า PM2.5/TVOC ที่เป็นตัวขับสถานะ)
3. การ์ดงานค้าง: อุปกรณ์ที่ควรเปลี่ยน/สอบเทียบเร็วที่สุด พร้อมจำนวนวันและปุ่มไป Maintenance
4. กราฟแนวโน้ม โดยเลือก 24 ชม., 7 วัน, 30 วัน หรือกำหนดเอง; ตัวชี้วัดเลือกได้ทีละรายการเพื่อไม่ให้หน่วยต่างกันทำให้กราฟอ่านยาก
5. ตารางสรุปรายวัน: วันที่, ค่าเฉลี่ย, ค่าสูงสุด, ชั่วโมงข้อมูลที่ใช้ได้, ระดับสี/จำนวนช่วงเกินเกณฑ์

### 2. ประวัติคุณภาพอากาศ

เพิ่มหน้า “ประวัติ” แยกจาก Dashboard หรือเพิ่มส่วนที่ชัดเจน พร้อมตัวกรอง:

- กล่อง/สถานี
- พารามิเตอร์ (PM2.5, PM10, TVOC, eCO₂, อุณหภูมิ, ความชื้น)
- วันเดียวหรือช่วงวัน และความละเอียด ชั่วโมง/วัน/เดือน
- สรุปค่าเฉลี่ย, ค่าสูงสุด, ค่าต่ำสุด และสัดส่วนข้อมูลที่วัดได้
- กราฟและตารางวันเดียวกัน เพื่อให้ดูได้ทั้งภาพรวมและค่าต้นทาง
- แสดงช่องว่างเป็น “ไม่มีข้อมูล” ไม่ลากเส้นต่อเนื่องให้ดูเหมือนมีการวัด
- เตรียม CSV export สำหรับนำไปตรวจวิเคราะห์/รายงาน

### 3. Maintenance และอะไหล่

- จัดลำดับรายการเป็น “ต้องทำตอนนี้ / เตรียมภายใน 30 วัน / ปกติ” ใช้ไอคอนและข้อความร่วมกับสี ไม่ใช้สีอย่างเดียว
- ต่อแถวอุปกรณ์แสดง: HI, แนวโน้ม 30 วัน, วันคงเหลือโดยประมาณ, วันที่ควรเปลี่ยน/สอบเทียบ, อะไหล่ที่ต้องเตรียม, เหตุผลหลัก และความเชื่อมั่น
- มีปุ่ม “บันทึกเปลี่ยน/ซ่อม/สอบเทียบ” ที่เก็บวันเวลา ผู้ทำ หมายเหตุ รุ่น/ล็อตอะไหล่ และค่าเริ่มต้นรอบใหม่
- แยกอายุที่ผู้ผลิตระบุ/กำหนดตามนโยบาย ออกจาก RUL ที่คำนวณจากสภาพจริง
- เมื่อข้อมูลไม่พอหรือระบบเป็น Mock ให้แสดง “ยังประเมินไม่ได้” หรือ “ตัวอย่าง” แทนจำนวนวันที่ดูแม่นยำเกินจริง

## นิยามคุณภาพและการคำนวณวันคงเหลือ

- **Health Index (HI):** คะแนน 0–100 โดยนิยามคุณลักษณะและช่วงอ้างอิงต่อเซนเซอร์ไว้ใน configuration และแสดงองค์ประกอบ (Drift, Noise, อายุ, ความครบถ้วน/ความผิดปกติ)
- **RUL (วัน):** ประมาณจากแนวโน้ม HI ตามเวลาและขีดจำกัดที่กำหนด หลีกเลี่ยงสูตรที่หารอายุหรืออัตราเสื่อมชุดเดียวกับตัวเองจนได้คำตอบคงที่
- ต้องสะสมข้อมูลสุขภาพเป็น time series พร้อมวันสอบเทียบ/เปลี่ยนอะไหล่ และมีช่วงข้อมูลขั้นต่ำก่อนรายงาน RUL
- ส่งคืน `rul_days`, `replacement_due_date`, `confidence`, `basis`, `last_calibrated_at`, `last_replaced_at`, `data_coverage_pct`, `model_version`
- ให้ผู้ดูแลกำหนด buffer สำหรับจัดซื้อ เช่น แจ้งเตือนเมื่อเหลือ 30 วัน และเตรียมอะไหล่ตามชนิด/จำนวน
- ระบุว่า RUL เป็นค่าประมาณเพื่อช่วยวางแผน ไม่ใช่การรับประกันอายุใช้งาน

## ข้อกำหนดบันทึกรายวันและข้อมูล

ทุก reading ต้องเก็บ `box_id`, `recorded_at` พร้อม timezone, ค่าดิบ, หน่วย, สถานะเซนเซอร์/ความถูกต้อง, firmware/model version เท่าที่มี การสรุปรายวันให้ระบุเขตเวลา Asia/Bangkok และเกณฑ์จำนวนชั่วโมง/ความครอบคลุมขั้นต่ำอย่างชัดเจน ควรเก็บข้อมูลดิบไว้เพื่อคำนวณสรุปใหม่เมื่อแก้เกณฑ์

แนะนำ API เพิ่มเติม:

- `GET /api/air-quality/daily?box_id=&from=&to=&parameter=` — สรุปต่อวัน พร้อม count/coverage/min/mean/max และสถานะ
- `GET /api/air-quality/history?box_id=&from=&to=&resolution=hour|day&parameter=` — อนุกรมข้อมูลที่กรองแล้ว
- `GET /api/maintenance/status?box_id=` — HI/RUL พร้อม basis/confidence/coverage และวันกำหนดงาน
- `POST /api/maintenance/events` — บันทึกเปลี่ยนอะไหล่/ซ่อม/สอบเทียบ พร้อมผู้ปฏิบัติงาน/หมายเหตุ/อะไหล่
- `GET /api/maintenance/events?box_id=&from=&to=` — ประวัติงาน

## เกณฑ์สีและการเข้าถึง

- ใช้สีเขียว = ปกติ, เหลือง/อำพัน = เฝ้าระวัง/เตรียมของ, แดง = เร่งด่วน, เทา = ไม่มีข้อมูล/ยังประเมินไม่ได้
- คู่กับป้ายข้อความและไอคอนทุกครั้ง; ตรวจ contrast และไม่สื่อความหมายด้วยสีอย่างเดียว
- ลดคำอธิบายยาวในหน้าหลัก ใช้ label ภาษาไทยสั้น หน่วยชัด; รายละเอียดเชิงเทคนิคอยู่ใน tooltip/หน้ารายละเอียด
- รองรับมือถือและตารางเลื่อนแนวนอนได้

## แผนดำเนินงาน

1. ทำหน้า History รายวันและ API aggregation โดยใช้ readings ที่มี และยกเลิก/ปรับ purge 30 วันหรือสร้าง daily summaries ก่อนลบข้อมูลดิบ
2. ออกแบบ schema/API สำหรับ maintenance events, baseline, sensor health snapshots และอะไหล่
3. แทน mock HI/RUL ด้วยข้อมูลจริง พร้อม data coverage และความเชื่อมั่น; จนกว่าจะมีข้อมูลพอให้แสดง “ประมาณการเบื้องต้น”
4. เพิ่ม inventory ขั้นต่ำ/จุดสั่งซื้อและรายการอะไหล่ตาม sensor/device
5. ทบทวนสี, ภาษาไทย, responsive และการแสดงข้อมูลขาดหาย
